# 커밋 단위 구현 워크플로

이 문서는 기능 종류와 무관하게 반복하는 구현, 검증, 독립 리뷰, 하네스 개선 절차를 정의한다. 제품별 결정과 작업별 세부사항은 계획 문서에 두고 여기에는 영속적인 작업 흐름만 남긴다.

## 기본 구현 루프

1. `AGENTS.md`, 현재 계획, 변경 대상 코드 경로와 작업 트리 상태를 확인한다.
2. 요청을 확인 가능한 성공 조건으로 바꾸고, 이번 커밋에서 변경하지 않을 범위를 적는다.
3. 하나의 목적과 검증 기준으로 설명 가능한 가장 작은 구현 단위를 선택한다.
4. 그 단위에 필요한 파일만 수정한다. 미래 작업을 위한 추상화나 인접 정리는 추가하지 않는다.
5. 성공 조건을 직접 확인하는 focused test 또는 동작 검증을 실행한다.
6. 하네스 개선 후보가 발견됐다면 아래 승격 기준으로 평가한다.
7. 프로젝트 `reviewer` sub-agent에게 변경 파일과 성공 조건을 전달해 독립 리뷰를 요청한다.
8. 유효한 지적을 최소 변경으로 수정하고 focused 검증을 다시 실행한다.
9. 같은 변경 범위를 다시 리뷰해 정확히 `No Findings`가 나올 때까지 7~8단계를 반복한다.
10. `AGENTS.md`가 요구하는 변경 앱의 전체 검증을 실행한다.
11. 전체 검증 실패로 파일을 수정했다면 focused 검증과 reviewer 반복으로 돌아간다.
12. 해당 구현 단위와 검증만 포함해 커밋하고 다음 단위로 넘어간다.

## 범위 제어

- 새 구조는 현재 성공 조건을 더 단순하게 충족할 때만 도입한다.
- 미래 요구, 아직 선택되지 않은 대안, 짧은 실험만을 위해 설정 계층이나 범용 인터페이스를 만들지 않는다.
- 현재 변경으로 사용하지 않게 된 코드만 제거한다. 인접한 오래된 코드는 별도 작업으로 남긴다.
- 계획 밖 변경이 필요하면 먼저 계획을 업데이트하고 범위가 넓어진 이유를 남긴다.
- 서로 다른 목적이나 롤백 단위를 하나의 커밋에 섞지 않는다.

## 리뷰 적용 기준

다음 변경은 기본적으로 독립 reviewer 검토 대상이다.

- 프로덕션 코드의 기능 추가와 버그 수정
- 여러 파일 또는 공통 계약에 영향을 주는 변경
- 인증, 개인정보, 데이터, DB, 검색, 분석, 배포 동작처럼 부작용 비용이 큰 변경
- 동작 보존을 전제로 하는 구조 변경과 리팩터링
- 저장소 전체 작업 방식에 영향을 주는 하네스 변경

다음 변경은 영향도가 낮고 다른 변경과 섞이지 않았을 때 리뷰를 생략할 수 있다.

- 단순 오타와 문구 수정
- 채택 전에 되돌릴 일시적 실험
- 동작이 명확한 작은 설정값 변경
- 사용자가 영향도를 이해한 상태에서 명시적으로 리뷰 생략을 요청한 변경

리뷰 생략은 테스트와 동작 검증 생략을 의미하지 않는다. 판단이 애매하면 리뷰를 수행한다.

## 하네스 개선 피드백 루프

버그, reviewer finding, 수동 검증 누락, 반복되는 작업 혼선이 발생하면 아래 순서로 판단한다.

1. 단순한 구현 실수인지, 현재 규칙이나 검증의 공백인지 구분한다.
2. 기존 규칙을 지키면 방지됐던 문제라면 중복 규칙 대신 기존 규칙의 가시성이나 실행 검증을 보강한다.
3. 규칙 공백이라면 아래 네 항목을 각각 0~3점으로 평가한다.
4. 승격 기준을 통과한 경우 가장 작은 방지 계층을 선택하고, 통과하지 않으면 작업별 계획이나 결과에만 남긴다.
5. 추가한 검증이 문제를 실제로 탐지하거나 예방하는지 확인한다.

### 하네스 승격 점수

- 심각도: 0은 외관상 문제, 1은 작은 로컬 불편, 2는 사용자 노출 또는 반복 작업 비용, 3은 보안/개인정보/데이터 손실/운영 장애/제품 신뢰 위험이다.
- 재발 가능성: 0은 일회성, 1은 드물지만 가능, 2는 인접 작업에서 반복 가능, 3은 여러 작업에 걸친 구조적 패턴이다.
- 탐지 난이도: 0은 일반 구현 중 명확, 1은 보통 리뷰에서 발견, 2는 명시적 검증 없이는 놓치기 쉬움, 3은 사용자 확인이나 운영 전까지 드러나기 어렵다.
- 검증 적합성: 0은 규칙화가 과도함, 1은 주의 문구만 가능, 2는 집중된 체크리스트나 reviewer 판단으로 확인 가능, 3은 저비용 자동 테스트나 검사로 강제할 수 있다.

합계가 8점 이상이거나, 심각도 3이면서 검증 적합성이 2점 이상일 때만 영구 하네스 변경으로 승격한다.

## 하네스 배치 원칙

가장 작고 실행 가능한 계층을 우선한다.

1. 결정적이고 저비용으로 재현할 수 있으면 회귀 테스트를 추가한다.
2. 명령으로 검사할 수 있으면 기존 검증 명령이나 CI를 보강한다.
3. 설계 판단이나 부작용 검토가 필요하면 reviewer prompt를 보강한다.
4. 반복 절차와 판단 기준이면 이 workflow를 보강한다.
5. 모든 작업에 적용되는 안정적인 행동 원칙일 때만 `AGENTS.md`를 보강한다.

특정 작업의 계획, 외부 서비스의 현재 상태, 일시적인 성능 수치, 개별 실패 로그는 영구 하네스에 넣지 않는다.

## 규칙 작성 계약

새 규칙이나 검증에는 다음 세 요소가 명확해야 한다.

- 적용 조건: 어떤 상황에서 이 규칙을 사용하는가.
- 요구 행동: agent가 무엇을 해야 하거나 피해야 하는가.
- 검증 지점: 테스트, CI, reviewer, workflow 중 어디에서 준수 여부를 확인하는가.

세 요소 중 하나라도 구체화할 수 없다면 영구 규칙으로 추가하지 않는다. 기존 규칙과 겹치면 새 항목 대신 기존 규칙을 합치거나 더 실행 가능하게 바꾼다.

## 작업 완료 보고

각 구현 단위를 마칠 때 다음을 남긴다.

- 변경 목적과 실제 변경 파일
- 실행한 focused 검증과 전체 검증
- reviewer 반복 횟수와 최종 `No Findings`
- 추가한 회귀 검증 또는 하네스 규칙
- 하네스 개선 후보를 승격하지 않았다면 그 이유
- 실행하지 못한 검증과 구체적인 blocker
