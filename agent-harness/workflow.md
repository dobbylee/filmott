# 커밋 단위 구현 workflow

구현을 시작할 때 읽는다. 검증 명령은 [testing](testing.md), 리뷰 입력/출력은 [review prompt](prompts/implementation-review.md)가 원본이다.

## 실행 순서

1. 작업 트리·사용자 변경·승인 범위를 확인하고 한 목적의 최소 커밋 단위와 성공 조건을 정한다.
2. 해당 Phase의 계약·파일만 읽고 구현한다. 전체 계획/이전 기록을 매번 다시 읽지 않는다.
3. 위험을 직접 확인하는 focused 검증을 수행한다.
4. 아래 리뷰 적용 기준에 해당하면 리뷰 프롬프트의 입력 묶음을 준비하고 독립 reviewer에게 전달한다.
5. 유효한 finding을 수정·검증하고 같은 reviewer에게 재리뷰한다. 정확히 `No Findings`를 받은 뒤 필수 전체 gate를 완료한다.
6. 전체 gate 실패로 코드가 바뀌면 affected focused 검사와 재리뷰를 수행한다. 변경 때문에 무효화된 gate만 다시 실행한다.
7. 검증한 해당 단위만 커밋하고 활성 작업 기록의 완료 근거·다음 행동을 갱신한다.

## 리뷰 적용과 컨텍스트

- 프로덕션 기능/버그/구조·공통 계약·여러 파일의 동작 변경·하네스 변경은 독립 리뷰 대상이다.
- 작은 오타/문구, 채택 전의 가역적 실험, 사용자가 리뷰 생략을 요청한 저위험 수정은 생략할 수 있다. 검증 생략을 뜻하지 않는다.
- 새 리뷰는 전체 대화를 상속하지 않는 호출을 우선한다(`fork_turns="none"`을 지원하면 사용). 모델은 상속하고 프로젝트 reviewer의 xhigh·읽기 전용 설정을 유지한다.
- reviewer에 전체 탐색 로그·과거 플랜을 붙이지 않는다. 관련 계약의 원문 위치와 변경 기준을 전달해 독립적으로 확인하게 한다.
- 같은 범위 재리뷰는 agent를 재사용하고 수정 요약·검증 결과·갱신된 변경 기준만 전달한다. 범위/목적이 바뀌면 새 리뷰로 구분한다.
- 읽기 전용 코드 감사는 `audit`, 계획 검토는 `plan`, 변경분 리뷰는 `diff`로 명시한다. 감사에 변경분 전용 제한을 적용하지 않는다.

## 검증 근거 재사용

- 결과에는 명령·종료 코드·시각·기준 SHA와 해당 범위의 작업 트리 상태/내용 식별값·중요 환경을 기록한다.
- 입력 코드·설정·의존성·fixture·중요 환경이 같은 완료 결과만 재사용한다. focused 일부 통과를 전체 gate 통과로 승격하지 않는다.
- 관계없는 문구 변경 때문에 앱 gate를 반복하지 않는다. 배포·DB 상태처럼 변하는 조건은 적용 직전에 다시 확인한다.
- local/CI/Production 결과를 구분하고, 실행 불가·표본 부족·미검증을 성공으로 기록하지 않는다.

## 커밋과 보고

- 계획 기반 구현은 단위별 검증 후 커밋한다. 계획 없는 작은 수정은 사용자가 커밋을 요청했을 때만 커밋한다.
- 제목은 영어 conventional prefix와 한국어 설명, 본문은 변경·검증·영향을 1~3문단으로 쓴다. 다른 목적의 수정은 나눈다.
- 완료 보고는 변경 목적·파일, 필수 검증, reviewer 결과, 생략과 이유를 간결하게 남긴다.
- 영구 하네스 변경을 검토할 일이 생겼을 때만 [승격 기준](promotion.md)을 읽고 그 판단을 해당 작업에 기록한다.
